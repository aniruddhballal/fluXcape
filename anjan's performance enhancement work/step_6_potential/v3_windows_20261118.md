Scope: only the first-field solve, gradients, scaling and three saved field files in step 6. Existing source code and V1/V2 modules are unchanged. The same input directory is used throughout: `../step_4_package/runs/20261118_192252_109811`.

## Research and hypothesis

Primary sources describe reusing stencil data in cache across multiple iterations to reduce memory traffic: [Intel cache-blocking guidance](https://www.intel.com/content/www/us/en/developer/articles/technical/cache-blocking-techniques.html) and [Treibig, Wellein and Hager, Efficient multicore-aware parallelization strategies for iterative stencil computations](https://arxiv.org/abs/1004.1741). [Numba parallel-loop documentation](https://numba.readthedocs.io/en/stable/user/parallel.html) requires independent parallel iterations. These sources motivated testing private temporal tiles; they do not predict a speedup on this laptop. All reported speedups below come from local measurements.

## Implementation

`optimised_laplace_v3.py` divides the x/y interior into independent 16 by 16 cores, with the full z axis per tile. A private halo allows four exact Jacobi updates before publishing the core to the global output buffer. The valid halo region shrinks each update. Tile halos are redundant work, not modified boundary conditions. All six global faces retain their original values. Field arithmetic, float64 precision, operation order, gradients, scaling, tolerance and iteration cap remain unchanged; fast-math stays disabled.

Each tile records its owned-core maximum change for every individual update. Unsigned float64-bit ordering and a global tile maximum retain V2's exact convergence comparison. The wrapper checks each update in order. If the first converged state lies inside a batch, it recomputes that prefix from the untouched batch input, discarding later speculative states. Thus it returns the first converged field, not the end of a batch. Metadata distinguishes logical updates, unused speculative updates and replayed updates.

Batches never cross progress labels 0, 50, 100, etc. Each logged error and elapsed timestamp therefore corresponds to its original global iteration boundary. CSV logs retain their existing schema. Metadata additionally retains exact final convergence error, tile/depth, actual worker count, threading layer and replay counts. Unsupported layouts/types and initially nonfinite inputs fall back to the original solver.

Selection: `--implementation optimised-v3 --first-field-only` through `measure_potential.py`. Original remains the default. V3 defaults to up to four workers; `NUMBA_NUM_THREADS` explicitly overrides it.

### Interpretation and limits

The improvement is consistent with cache reuse seen in the paired tile benchmarks, not a change to Jacobi arithmetic, precision, convergence settings, grid or gradients. The exact contribution of memory traffic versus scheduling/compiler effects was not separately profiled. V3 used more sampled peak RAM than V2. RSS and cumulative CPU are sampled every 100 ms and may miss short peaks; CPU seconds sum parallel work across cores. Previous implementations remain unchanged and available. This validates a further improvement on this observation and device, not a global performance maximum or a guarantee for other hardware.
